# M1-03-控制接口与频率延迟

> 本页属于：stackforce 机器狗实战（M1 实操）
> 前置知识：[[M1-02-Joint-Map与单执行器]]
> 预计阅读时间：20 分钟

## 🎯 为什么需要这个？

搞清楚 actuator 到底接受什么 command，以及真实控制频率/延迟——这两件事直接决定 RL 的动作设计和仿真步长。

## M1.5 测真正的控制接口

StackForce actuator 接受的 command 可能是：

```text
Position      q_d
Velocity      dq_d
Torque        τ_d
MIT-style     τ = Kp(q_d - q) + Kd(dq_d - dq) + τ_ff
```

**必须从固件/API 明确确认。**

如果支持 `q_des / dq_des / Kp / Kd / tau_ff`，就非常适合：

```text
RL Policy → desired joint position → PD → motor
```

第一版 Sim-to-Real 推荐这种方式，而不是 RL 直接输出 torque。

## M1.6 测控制频率和延迟

这一步很多人跳过，但后面 Sim-to-Real 非常关键。要测：

```text
Sensor rate :  f_IMU = ? Hz    f_encoder = ? Hz
Command rate:  f_control = ? Hz
延迟        :  t_command → t_motion 大约差多少
```

假设最后发现：

```text
Motor inner loop     1000 Hz
State reading         500 Hz
Host communication    200 Hz
RL policy             100 Hz
```

那么 Isaac Lab 应设计：

```text
Δt_policy = 0.01 s
```

而不是随便选 60 Hz。

## ✏️ 小练习

**1.** 为什么第一版推荐 position+PD 而不是 torque？

<details>
<summary>查看答案</summary>

position+PD 更安全、更好训练、更好 Sim-to-Real；直接 torque 对模型误差敏感，实机风险高。
</details>

**2.** Δt_policy 应该怎么定？

<details>
<summary>查看答案</summary>

按真实 RL 策略/通信频率定（如 100 Hz → 0.01 s），让仿真与实机控制节奏一致。
</details>

## 本章小结

- 明确 command 类型（position/velocity/torque/MIT-style）。
- 第一版用 position+PD。
- 测 sensor/command 频率与延迟，据此定 Δt_policy。
